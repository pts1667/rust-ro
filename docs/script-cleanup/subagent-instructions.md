# Cleaning up one generated NPC script

You clean up one generated NPC script so it reads like hand-written Rust. The behaviour must not change. You have no other context, so this file is everything you need. Read it fully before editing.

## What you are working on

The file you are given is generated Rust in `scripts/<module>/src/`. It uses the `script-sdk-2` API (`lib/script-sdk-2`, summarised below and described in `docs/script-sdk-2.md`). Each NPC or event is a `pub fn name(ctx: &Ctx) -> Script`. Some have a private `*_run(ctx, step, args)` state machine next to them, which the generator emits for scripts that jump between labels.

The generator produced code that is correct but hard to read:

- Long chains of nested `if`/`else` on one variable, each level wrapped in `{ ... }`.
- `ctx.call(Function::DelItem, vec![Val::from(535), Val::from(10)])?` for every call, when `args![535, 10]` is the same thing.
- Local variables as `l_name`, cloned at every comparison (`l_x.clone() == 1`).
- Dead locals and unused `mut` (`let mut l_arg = Val::from(0);` that is never read).
- Multi-screen dialogues written as deeply nested calls, not as a sequence of steps.

## Hard rules

1. **Same behaviour.** The same host calls happen in the same order with the same arguments. The same dialogue text is shown, character for character, including typos and spacing. The same variables are written. Each script ends the same way (`ctx.close()` stays `ctx.close()`, `ctx.end()` stays `ctx.end()`, `ctx.close_window()` stays `ctx.close_window()`).
2. **Only the named file.** Edit only the file you were given. Do not edit `lib.rs`, `shared`, other NPC files, `Cargo.toml`, anything under `config/`, or anything under `tools/`. Do not run the generator, and do not copy or build any `.wasm`.
3. **Keep the public surface.** Keep every `pub fn` name and signature. The module's `lib.rs` registry refers to them by path, and keys like `"Charles Orleans#cook_"` must still resolve. Do not rename anything that is `pub`.
4. **Do not reorder reads.** Moving a call past dialogue is a behaviour change, with one exception: `StrCharInfo`, `GetItemName`, `GetItemInfo` and `GetAreaUsers` are read-only lookups. You may compute those before a dialogue line, but only if you keep their results in the same text.
5. **Do not swap a helper for a typed wrapper unless it sends the same request.** Before replacing `ctx.call(Function::X, ..)` with a wrapper such as `ctx.items().give(..)`, open the wrapper's source in `lib/script-sdk-2/src/` and confirm it calls the same `Function` with the same arguments in the same order. If it does not, keep the `ctx.call`.
6. **Comments.** Write new comments only where the code cannot say what it does. Keep comments short and useful to a future developer. Do not write comments that repeat the code, and do not comment obvious steps. Do not delete existing comments.
7. **Stop when unsure.** If a rewrite would need a guess about what the original does, leave that part as it was and say so in your report.

## Marking the file

The generator rewrites every file under `scripts/<module>/src/` unless the file is marked as hand-maintained. Once you have cleaned the file, make the first line of it exactly this:

```rust
// hand-maintained: the generator leaves this file alone
```

- Put it above everything else in the file, including any old `// Generated by ...` or "Do not edit" comment. Delete that old comment.
- The marker covers the whole file, not just the NPC you cleaned. Other NPCs in the same file are also no longer regenerated.
- If you find that the generated code for this NPC needs a change to the generator, do not regenerate or hand-edit around it. Report it, and leave the file as it is.

## The API you will use

| Call | Meaning |
| --- | --- |
| `ctx.mes(text)` | One dialogue box. `\n` breaks lines. |
| `ctx.mes_as(speaker, text)` | Same, with a `[speaker]` title line first. |
| `ctx.next()` | Waits for the player to press next. |
| `ctx.menu(&["A", "B"])?` | Shows options and returns the 0-based index. Cancel is an error that propagates with `?`. |
| `ctx.close()` / `ctx.end()` | Closes and ends the script, as `Script`. |
| `ctx.close_window()?` | Closes the window and keeps running. |
| `ctx.var("name").get()?` / `.set(v)?` | Reads and writes a rathena variable. |
| `ctx.call(Function::X, args![a, b])?` | Calls a host function. |
| `args![a, b]` | Builds a `Vec<Val>` from numbers and strings. |
| `Val::from(..)` | Builds a number or text value from `i32`, `bool`, `&str`, `String`. |
| `val.number()?` | The value as `i32`. Errors if it is text. |
| `val.text()` | The value as text. |
| `val.is_true()` | Truthiness, as rathena uses it. |

Comparisons: `val == 5` and `val == "5"` compare by text when the types differ, as rathena does. `val < 5` orders numbers only, and a text is never less than or greater than a number.

## Cleanup steps, in order

Work through these in order and skip any that do not apply.

1. **Flatten nested `if`/`else`.** Replace `else { if c { .. } else { .. } }` with `else if`. Chains on one variable can become `match`, but see the warning below.
2. **Use `args!`.** Replace `vec![Val::from(a), Val::from(b)]` with `args![a, b]`.
3. **Remove clones in comparisons.** `l_x.clone() == 1` can become `l_x == 1` when `l_x` is `Val` and the comparison is by value. Check the type first.
4. **Remove dead code.** Delete locals that are never read, and `mut` that is not needed. Delete the `#![allow(..)]` lines at the top of the file only if the file compiles without them.
5. **Turn step-by-step dialogue into state.** When a conversation moves through several menus and screens, and the screens lead back to each other, write one `enum` variant per screen (named for what it does, such as `AskJob`, `Confirm`) and a `loop { match state { .. } }`. Keep it only when the flow really loops or jumps. A straight-line conversation stays as plain code.
6. **Use typed wrappers** only under rule 5 above.

**Warning on `match`.** `Val` compares loosely. In rathena, a text value is never equal to a number, and `.number()?` raises an error on text. So `match x.number()? { 1 => .. }` changes behaviour when `x` could hold text. Use `match` or `.number()?` only when the value is always a number, for example a local that only ever gets numeric literals or arithmetic results. When in doubt, keep `== 1` on the `Val`.

## Example

Before:

```rust
if l_new_book.clone() == 1 {
    ctx.call(Function::DelItem, vec![Val::from(535), Val::from(10)])?;
    ctx.call(Function::GetItem, vec![Val::from(7472), Val::from(1)])?;
} else {
    if l_new_book.clone() == 2 {
        ctx.call(Function::DelItem, vec![Val::from(538), Val::from(5)])?;
        ctx.call(Function::GetItem, vec![Val::from(7473), Val::from(1)])?;
    } else {
        if l_new_book.clone() == 3 {
            ctx.call(Function::DelItem, vec![Val::from(551), Val::from(5)])?;
            ctx.call(Function::GetItem, vec![Val::from(7474), Val::from(1)])?;
        }
    }
}
```

After, if `l_new_book` is always a number (rule above):

```rust
match l_new_book.number()? {
    1 => {
        ctx.call(Function::DelItem, args![535, 10])?;
        ctx.call(Function::GetItem, args![7472, 1])?;
    }
    2 => {
        ctx.call(Function::DelItem, args![538, 5])?;
        ctx.call(Function::GetItem, args![7473, 1])?;
    }
    3 => {
        ctx.call(Function::DelItem, args![551, 5])?;
        ctx.call(Function::GetItem, args![7474, 1])?;
    }
    _ => {}
}
```

If you cannot show `l_new_book` is always a number, use `if`/`else if` on `l_new_book == 1` instead. That is still flat and keeps the loose comparison.

## Checking your work

1. Run `rustfmt --edition 2021 <your file>`.
2. Run `cargo check --manifest-path scripts/<module>/Cargo.toml --target wasm32-unknown-unknown --locked`. It must pass.
   - If it fails in a file you did not touch, stop and report it. Do not fix other files.
3. Do not build the release wasm or run the trace test. The orchestrator runs those on the whole module after your change, and a mismatch is reported by NPC name.

## Report

End with a short report, no more than 15 lines:

- The file you changed, and the NPC or event names in it.
- The cleanup steps you applied, with counts.
- What you left as it was, and why (for example, "`l_new_book` may be text, so kept `== 1`").
- The result of `cargo check`.
- Anything you are unsure about. Say what would settle it.

Do not claim the behaviour is unchanged unless you verified it. Say "not run" for anything you did not run.
