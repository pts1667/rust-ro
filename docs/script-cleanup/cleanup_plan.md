# Cleanup of the generated scripts: plan for the orchestrating agent

This document is the brief for a fresh session. You are the orchestrator of a large, mostly mechanical refactor: about 285 generated Rust files under `scripts/` have to be rewritten so that they read like hand-written code, without changing behaviour. You do not rewrite the files yourself. You launch one cheap subagent per file, compile the results, and send failures back.

You should run 3 Haiku 5.5 subagents with high reasoning, and rotate (reuse) them between the file cleanup tasks for code consistency.

## Background

- The server (a pre-renewal Ragnarok Online server in Rust) runs NPC and event scripts as WebAssembly modules built from the crates under `scripts/` (`towns`, `misc`, `jobs`, `quests`, `shared`, plus `items`, `pets`, `systems`). Their sources were generated from rAthena's NPC scripts by `tools/scripts-import/convert_npcs.py`, and written against the `script-sdk-2` API (`lib/script-sdk-2`, `docs/script-sdk-2.md`).
- The generated code is correct but hard to read (nested `else { if .. }` chains, `vec![Val::from(..)]` everywhere, `l_x.clone()`, mechanical `switch` and menu lowering). The generator is not going to be improved further; the files are now hand-maintained.
- The generator rewrites a file under `scripts/<module>/src/` only if its first line starts with `// Generated by tools/scripts-import/convert_sdk2.py`. A subagent that finishes a file deletes that line, which marks the file as hand-written for good. So "first line still present" means "not cleaned yet".
- `docs/script-cleanup/subagent-instructions.md` is the complete brief of a subagent. Subagents do not read CLAUDE.md or anything else, so read that file first: it defines what they may change, which rewrites are safe, and what their report contains. It was written without a model having tried it, hence the pilot below.
- A cleanup changes no behaviour, so there is no test in this round. The only check is that each module still compiles.

## Rules for you

- Do not commit, push or create branches unless the user asks. Report, and ask.
- Do not run `tools/scripts-import/convert_npcs.py --write` or any other generator, and do not build `.wasm` files.
- Never compile a module while subagents are still running: a file that an agent has half edited breaks the check for everyone. Compile only at the checkpoints of step 4 under "Running the cleanup".
- Mostly stay out of the script files yourself, except to restore one with `git checkout -- <file>`. Do not hand-fix what a subagent got wrong: send it back (see "Running the cleanup").
- Exception to the above: it's fine to do this once in a while to check for consistency, but keep manual script reads rare and small.
- Comments in code follow the project policy: only where the code cannot say it, short, none that repeat the code, and never delete existing ones. This also goes for what the subagents write.

## Before you start

1. Run `git status`. The working tree should be clean, because `git checkout -- <file>` is how you roll a file back, and the cleanup diffs should not mix with anything else. If there are uncommitted changes, tell the user and ask whether to commit them first.
2. Read `docs/script-cleanup/subagent-instructions.md`.
3. Create `docs/script-cleanup/report.md` with a table `| File | Status | Notes |`. You fill it in as you go. A status is `cleaned`, `untouched` (the agent decided to leave the file, with its reason) or `restored` (it failed to compile twice and was rolled back). Files with a status other than `cleaned` are excluded from every later round, otherwise they come back in the candidate list forever.

## Scope: which files

A file is a candidate when all of these hold:

- It is under `scripts/towns/src`, `scripts/misc/src`, `scripts/jobs/src`, `scripts/quests/src` or `scripts/shared/src`.
- Its first line starts with `// Generated by tools/scripts-import/convert_sdk2.py from`.
- It is not a `lib.rs` (the registry) or a `mod.rs`.
- It has at most 3,000 lines. The larger ones are in the appendix: they are left alone.

`scripts/items`, `scripts/pets` and `scripts/systems` are not in scope (the first two are emitted by their own importers, the last is hand-written already).

List the candidates still to do:

```bash
for f in $(find scripts/{towns,misc,jobs,quests,shared}/src -name '*.rs' ! -name lib.rs ! -name mod.rs); do
  head -1 "$f" | grep -q '^// Generated by tools/scripts-import/convert_sdk2.py from' && [ "$(wc -l < "$f")" -le 3000 ] && echo "$f"
done
```

At the time of writing that is 285 files and about 192,000 lines: `towns` 64, `misc` 79, `jobs` 31, `quests` 68, `shared` 43. Subtract the files in `docs/script-cleanup/report.md` that are not `cleaned`.

## Running the cleanup

1. **Pilot.** Pick five small files from `towns` (for example under `scripts/towns/src/airports/`) and launch one subagent for each, three at a time, then read the diffs and the reports yourself. You are looking for a changed string or number, a moved call, a menu comparison renumbered wrongly, a `switch` turned into a `match` although a case fell through, anything the instructions did not foresee. Include at least one file with `runtime::op` calls (`grep -rl runtime::op scripts/towns/src`) and one with many `ctx.constant(` calls: the instructions let agents turn those into plain comparisons and `constants::NAME` (declared in `lib/script-sdk-2/src/constants.rs`), and the usual mistakes are `.number()?` on a text (a `$`-named variable), a `&str` constant used as a number, and a changed `Val` type that another line still uses. Compile `towns`. If an agent misunderstood the instructions, fix `docs/script-cleanup/subagent-instructions.md` (the only document you may edit besides `docs/script-cleanup/report.md`) and run the pilot again on other files. Do not scale up before the pilot is clean.
2. **Run the agents, three at a time.** One subagent per file, with the Agent tool: `subagent_type` `general-purpose`, `model` `haiku` (Haiku 5.5), `effort` `high`, in the background. Keep at most three running. The prompt is:

   > Read `docs/script-cleanup/subagent-instructions.md` in the repository root, then clean up `<path>` as it describes. Reply with the report it asks for.

   Replace `<path>` with the repository-relative path, such as `scripts/towns/src/airports/einbroch.rs`. Agents edit different files, never compile, and never change git state, so they run in parallel without worktrees. Work in this order: `shared`, `towns`, `misc`, `jobs`, `quests` (`shared` first, because the other crates depend on it, so a break there shows up everywhere). Inside a module go smallest file first. When one agent finishes, you may start the next; wait for completion notices and do not poll.
3. **Collect the reports.** Each ends with a report of at most 15 lines. Put the file in `docs/script-cleanup/report.md` with its status and the "left as it was" and "unsure" notes. An agent that stopped without a report (out of context, for instance) usually left the file half edited: run `git diff --stat -- <file>`, and if it changed, restore it with `git checkout -- <file>` and mark it `untouched` with the reason. If several agents fail that way on large files, lower the 3,000-line limit for the rest of the run.
4. **Compile at checkpoints**, with no agent running. After every 15 finished files (five rounds of three), and when a module has no candidate left, stop launching, wait until all running agents are done, then run:
   ```bash
   cargo check --manifest-path scripts/<module>/Cargo.toml --target wasm32-unknown-unknown --locked
   ```
   `towns` takes about 8 seconds; the large modules (`quests`, `misc`) take longer, not measured yet. A warning is not an error: one `game-towns` warning exists already. A syntax error stops rustc before it reports type errors, so repeat the check until it is clean. Only the files since the last checkpoint can be at fault; `git diff --stat` lists them.
5. **Fix failures.** Every error names a file. Send the error text back to the agent that cleaned the file (`SendMessage` to its id; load the tool with ToolSearch if it is not available), or start a new subagent with the file and the error text. A file that still fails after two rounds is restored with `git checkout -- <file>` and marked `restored`.
6. **Repeat** until no candidate is left. Then run the compile for every module once more, in the order above.

## Done when

- The candidate list is empty, apart from files marked `untouched` or `restored` in `docs/script-cleanup/report.md`.
- All five modules compile with `cargo check`.
- You report to the user: how many files were cleaned, `untouched` and `restored`, the notable "unsure" items from the reports, and that nothing was run beyond the compiler. Then ask whether to commit, one commit per module being the natural split.

## Not part of this round

- No trace replay and no behaviour test. Offer it to the user at the end: build the modules with `cargo run --package tools --bin scripts-build` (source in `tools/scripts-build/main.rs`), then run `cargo test --release -p server npc_trace`. The snapshot `server/src/server/script/npc_traces.json` should replay with no difference, since a cleanup must not change behaviour. A difference names the module and entry of the script that changed.
- No generator change and no regeneration. If someone runs `convert_npcs.py --write` later, it skips the cleaned files and prints how many it skipped, but it still rewrites each module's `lib.rs` and `mod.rs`.
- The `#![allow(..)]` lines and the unused names in the `use` lines stay. Removing them is a follow-up that needs the compiler's warnings.
- The large files below. Splitting them per NPC would need a generator change.
